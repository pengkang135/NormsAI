# 图片型PDF — 定额数据问题修复方案

## 适用范围

图片型PDF经OCR→AI转换→入库后的数据质量问题修复。问题的根因、分类和修复策略具有通用性，适用于任何扫描版定额PDF的提取后修正。

## 问题分类体系

OCR+AI流水线产出的数据质量问题可归纳为5类根因：

### 类型1：AI转换格式错误 — 并排/复杂布局未正确处理

**现象**: MD表格列数与实际数据不匹配，导致整列数据丢失或错位。

**根因**: 原PDF为复杂布局（左右并排、嵌套子表等），AI未能识别布局特征，用错误的列结构展开。

**通用触发条件**:
- 页面包含左右并排的两个独立子表
- 页面x方向存在>40%页宽的大gap
- 同一页面上存在两个独立的费用项目列表

**影响**: 整页或半页数据不可用。

### 类型2：AI转换遗漏 — 基价行/汇总行未被生成

**现象**: MD中缺少基价行。材料/机械/人工行正常，但最后缺少汇总行。

**根因**:
- AI在逐行展开时遗漏了最后一个或某几个定额编码的汇总行
- 复杂表格结构（分组子标题嵌入表格中间）导致AI整体解析失败

**影响**: 部分定额编码无总价基数，无法直接用于报价。

### 类型3：AI转换错误 — 行数据映射到错误的定额编号

**现象**: MD中存在数据行，但使用了错误的定额编号或属性列为空，加载器无法匹配。

**根因**: AI生成数据行时错误地自增/自减了编号；空属性列导致 `_align_cells` 对齐失败。

**影响**: 部分定额编码缺少关键行数据。

### 类型4：OCR残损传播 — 乱码/缺字未修正

**现象**: 费用项目列含乱码，amount列含非数值文本。

**根因**: OCR低置信度区域的错误被原样传入MD，未经过滤或领域知识修正。

**通用OCR错误类型**:
- 形近字误识别（如"围抢"→"围堰"、"冻士"→"冻土"）
- 字体粘连导致数字拆分错误
- 低分辨率区域字符丢失
- 噪声前缀混入（页码、页眉混入数据区）

**影响**: 个别行数据不可用。

### 类型5：原文档留空 — 非数据质量问题

**现象**: amount为 `---`（原文档无此项）、括号数值 `(10.20)`（参考值/可选值）、范围值 `920-1560`。

**根因**: 原定额文档中的排版约定，非提取错误。

**影响**: 无需修复，但需要在报价阶段正确解读这些值的语义。

## 修复策略（三级体系）

按修复方式分为三级，适用于任何图片型定额提取项目：

### A级：重做AI转换

**适用范围**: AI转换整体失败的页面（并排布局未识别、整表结构错误等）

**修复方法**:
1. 分析原PDF对应页面的布局特征
2. 增强AI prompt中的布局指引：
   - 识别并排布局（通过OCR x坐标 gap > 40% 页宽判断）
   - 对复杂表格提供表头展开指引
   - 确保转换后立即验证（基价存在、amount可解析）

**预估**: 占总页面的3-5%

### B级：MD文件手工修复（AI辅助）

**适用范围**: MD基本正确，仅缺少个别行或属性有误

**修复方法**:
1. 阅读原始MD文件和OCR JSON
2. 对比相邻正确编码的数据判断缺失/错误值
3. 手工补全或修正MD表格中的具体行

**预估**: 占总页面的1-3%

### C级：加载器增强（代码修复，一次性投入）

**适用范围**: 通过改进 `load_md_to_sqlite.py` 可自动修复的系统性问题

#### C1: `_align_cells` 增强

对非标准列数的处理：
```
策略：识别费用项目列（通过关键词匹配：人工/材料/机械/基价/船机）
将费用项目之前的列归入属性区，费用项目及其后归入数据区
支持 3-8 列等非标准列数的对齐
```

#### C2: 非数值 amount 处理增强

```
规则：
1. "---"、空字符串 → NULL（原文档留空，非错误）
2. "(10.20)" → 10.20（去括号转数值，标记data_quality='parenthesized'）
3. "920-1560" → 保留字符串，标记 data_quality='range'
4. 其他不可解析 → 记录 WARNING 日志，保留原文
```

#### C3: 基价缺失检测

在 `parse_tables` 完成后，对每个 norms_code 检查是否有基价行。如缺失，打印 WARNING 日志并记录到问题清单。

#### C4: `clean_cost_item` 修正

```
问题：过宽的正则可能误杀含型号数字的费用项目名（如 "M20水泥砂浆" → "水泥砂浆"）
修正：仅过滤纯数字或以纯数字开头的费用项目名（明显是OCR金额误入），保留含型号/规格的费用项目名
```

## 推荐执行顺序

```
第1步: C级加载器增强（一次性代码投入）
   ├── C2: amount 清理规则
   ├── C4: clean_cost_item 正则收窄
   ├── C1: _align_cells 增强
   └── C3: 基价缺失检测日志

第2步: 重新入库，评估剩余问题
   └── load_md_to_sqlite.py 全量重跑

第3步: B级 MD手工修复（针对少量残留问题）

第4步: A级 AI重转换（针对整体失败的少数页面）
```

C级修复通常可解决 70-80% 的问题（所有 amount 格式问题 + 部分对齐问题）。剩余约 20% 需要 B 级或 A 级修复。

---

## 验证标准

每步修复后验证：

| 指标 | 目标值 |
|:---|:---|
| amount为空的行 | 仅原文档留空的行 |
| 缺少基价的定额编码 | 0 |
| amount含非数值文本 | 0（范围值除外，标记为range） |
| 基价覆盖率 | 100% |
| 定额编号连续性 | 无空隙/重叠 |

## 附录：问题诊断方法

当发现数据质量问题时，按以下步骤诊断根因：

1. **定位问题页面**: 从 SQLite 查询异常的 norms_code 关联的 page
2. **对比 MD 原文**: 查看对应 `page_XXXX.md` 的表格部分
3. **回溯 OCR 数据**: 查看对应 `ocr_XXXX.json` 的原始坐标和文本
4. **确认 PDF 页面**: 渲染对应页面截图与原PDF对比
5. **归类根因**: 对照上述5种类型确定修复策略
